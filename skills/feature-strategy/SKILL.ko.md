# Feature Strategy

큰 스토리를 **사람이 단계마다 직접 화면과 코드를 확인할 수 있는 크기**의 하위 작업으로 나누고, 각 하위 작업 본문만 읽어도 에이전트가 바로 이어서 진행할 수 있게 만든다.

> **명시 호출 전용.** "쪼개줘", "계획 세워줘" 같은 일상적인 요청만으로 이 워크플로를 시작하지 않는다. 사용자가 `/feature-strategy`를 호출할 때만 실행한다.
>
> **적용 범위.** UI 중심 피처(화면, 모달, 디자인 파일)에 맞춰져 있다. 백엔드 등 다른 작업에는 같은 사이클을 적용하되, UI 관련 예시(모달, 훅, Figma, `NODE_ENV`)는 설명용 예시로만 읽는다.

## 시작 지점

입력을 확인하고 맞는 Phase에서 시작한다.

| 입력 | 시작 Phase |
|---|---|
| 디자인 링크, 또는 Phase A의 5개 섹션이 없는 스토리 | Phase A |
| Phase A의 5개 섹션이 채워져 있고, 하위 작업 01–02를 막는 확인 필요 사항에 답이 있는 스토리 | Phase B (입력 확인부터) |
| 5개 섹션은 있지만 비어 있는 섹션이 있거나 막는 질문에 답이 없는 스토리 | Phase A (A-3: 답변 채우기) |
| 하위 작업 키 (+ 디자인 섹션 링크) | Phase C |

사용자가 Phase를 지정하면 그대로 따르되, 필요한 입력이 없으면(예: 하위 작업 본문 없이 Phase C 요청) 멈추고 알린다.

## 용어

| 용어 | 의미 |
|---|---|
| 스토리 | 피처 단위 상위 이슈 (Jira Story, Linear Issue 등) |
| 하위 작업 | 스토리 아래의 구현 단위 이슈 (Sub-task 등) |
| 디자인 파일 | Figma 등의 디자인 산출물 |
| API 계약 | 백엔드 요청/응답 스키마 (DTO, OpenAPI 등) |
| 피처 문서 | 이 피처의 결정 기록과 진행 로그를 담는 로컬 문서 (예: `docs/feature/<KEY>-<slug>.md`) |

## 전체 사이클

```
Phase A. 스토리 사전 정의   디자인 → 요구사항 문서 → 스토리 본문 → 확인 필요 사항 답변
   ↓
Phase B. 하위 작업 플래닝   입력 확인 → 사실 조사 → 크로스체크 게이트 ─┬─ 통과 ──────────────────────┐
                                                                      └─ 재검증 1회 → 스토리 최상위 갱신 ┘
                            → 질문 라운드 → 로드맵 → 하위 작업 생성 → 피처 문서
   ↓
Phase C. 하위 작업 단위 구현  착수 → 구현 → 커밋 전 멈춤 → 사람 확인 → 커밋 → 다음 작업 보강
   ↺ 하위 작업 수만큼 반복 (첫 작업이 끝나면 Draft PR/MR)
```

| Phase | 권장 실행 환경 | 입력 | 산출물 |
|---|---|---|---|
| A | 큰 디자인 파일을 잘 읽는 환경 (데스크톱 앱, 디자인 도구 연동 등) | 디자인 링크, 기획 문서 | 스토리 본문: 화면 구성 ~ 확인 필요 사항 |
| B | 코드베이스에 접근 가능한 코딩 에이전트 | 스토리 + 코드베이스 | 하위 작업 N개, 피처 문서 |
| C | 코딩 에이전트 | 하위 작업 + 피처 문서 + 섹션별 디자인 링크 | 하위 작업 단위 커밋, Draft PR/MR |

## 핵심 원칙

1. **사실은 에이전트가 찾고, 결정은 사람이 내린다.** 코드나 이슈에서 확인할 수 있는 것은 묻지 않는다.
2. **큰 흐름 먼저.** 진입 동선과 레이아웃 → 검증 → 편집 → 동작 → API 연동 순서로 진행한다.
3. **API 계약이 없어도 막히지 않는다.** 계약 없이 할 수 있는 작업을 로드맵 앞쪽에 둔다.
4. **기존 코드를 보호한다.** 기존 컴포넌트는 고치지 않고 새 컴포넌트로 대체한다. 정리·리팩터링은 새 코드에만 한다.
5. **체크포인트마다 멈춘다.** 하위 작업 하나를 구현하면 커밋하기 전에 사람의 확인을 받는다.

---

## 이슈 트래커가 없을 때

트래커가 없거나 사람이 이슈 생성을 원하지 않으면, 같은 사이클을 유지하되 피처 문서를 단일 기준 문서로 쓴다.
- Phase A: 스토리 본문 대신 피처 문서 맨 위에 5개 섹션을 쓴다.
- Phase B: 로드맵과 하위 작업 본문을 피처 문서의 섹션으로 쓴다(템플릿은 동일). "실행 시 주의"의 트래커 단계는 건너뛴다.
- Phase C: 요청과 커밋 메시지에서 하위 작업을 로드맵 번호(`01`, `02`, …)로 부른다.

---

## Phase A. 스토리 사전 정의

목표: 기획·디자인 산출물을 **개발자가 판단할 수 있는 요구사항 문서**로 바꿔 스토리 본문에 넣는다. Phase B는 이 본문을 기준으로 진행한다.

### A-1. 디자인 → 요구사항 문서화
요청 예시:
```
"<디자인 링크(프레임/노드 ID 포함)>
여기 디자인 내용을 읽어보고 요구사항을 문서화 해줘."
```
- 디자인 페이지 전체가 매우 크면(수만 px, 수백 개 프레임), 디자인 도구 MCP의 메타데이터나 디자인 컨텍스트 응답이 크기 제한을 넘어 실패할 수 있다. 실행 환경마다 처리 방식이 달라서, 같은 링크라도 어떤 환경에서는 바로 분석되고 어떤 환경에서는 실패한다.
  - 그래서 **페이지 전체 분석은 큰 파일을 잘 처리하는 환경에서** 한다.
  - 코딩 에이전트에서는 하위 작업 단위 섹션(프레임) 링크로 상세 디자인만 확인한다.
- 구버전이나 검토용 섹션("~ to be", 표지만 있는 섹션 등)은 최신안인지 불명확하면 문서에서 빼고 "확인 필요 사항"에 올린다.

### A-2. 스토리 본문에 반영
요청 예시:
```
"이 스토리의 본문에 '화면 구성' 항목부터 추가해줘."
```
본문 맨 위의 "관련 문서" 링크(기획서, 디자인, 분석 결과)는 유지하고, 그 아래에 다음 섹션을 순서대로 쓴다.

| 섹션 | 내용 | Phase B에서의 쓰임 |
|---|---|---|
| 화면 구성 | 흐름별 표: `# / 흐름 / 진입점 / 주요 화면·컴포넌트 / 완료 결과`, 앱별 화면 경로 | 로드맵 대분류, 진입점별 첫 작업 |
| 기능 요구사항 | 흐름별 `FR-NN` 표 (ID 연번) | 하위 작업의 "관련 FR", 범위 경계 |
| 데이터·필드 정의 | 화면(모달·목록 등) 항목을 모드별 표시/편집으로 정리, 번호 형식, 상태 목록 | 컬럼/필드 정의, API 요청 필드, mock 타입 |
| 정책·예외 처리 | 검증 우선순위 표(순위/조건/메시지 제목/본문), 입력 검증, 연쇄 정책 | 검증 작업, 에러 메시지 문구 |
| 확인 필요 사항 | 디자인만으로 정해지지 않는 항목 목록 | 질문 라운드 전에 확정할 사항 |

작성 규칙:
- 화면 문구(토스트, 모달 제목·본문, 툴팁)는 **디자인 원문 그대로** 쓴다. 구현할 때 그대로 복사해 쓰기 위해서다.
- 디자인끼리 서로 어긋나는 부분(예: 같은 번호가 화면마다 다른 형식)은 하나를 고르지 않고, "확인 필요 사항"에 후보를 모두 나열한다.
- 예시 숫자로 규칙을 역산할 수 있으면 역산 결과를 적는다(예: "10단위 절사 + 나머지는 마지막 항목"이면 예시와 일치).

### A-3. 확인 필요 사항 답변 채우기 (사람)
- 기획·디자인·백엔드 담당자와 확인한 답을 **각 항목 바로 아래에 들여쓰기로** 적는다. 예: "백엔드에서 정의 예정", "저장 시점에 검증", "해당 영역 무시".
- 답이 코드 기준이면 코드 식별자를 적는다(예: "`useValidateSelection`에 옵션 추가").
- Phase B는 **답이 달린 항목을 확정 사항으로 보고**, 답이 없는 항목만 다시 묻는다.
- Phase B로 넘어가는 기준: 첫 2개 하위 작업(진입 동선, 레이아웃)을 막는 항목에 모두 답이 있어야 한다. 나머지는 "백엔드 확인", "API 대기"로 두고 진행해도 된다.

## Phase B. 하위 작업 플래닝

### 1. 입력 분석
- 스토리를 전체 필드로 조회하고, 관련 문서 링크와 Phase A 섹션을 확인한다.
- 다른 일을 하기 전에 **스토리가 실제로 채워져 있는지** 확인한다: 5개 섹션이 모두 있고 비어 있지 않으며, 하위 작업 01–02를 막는 확인 필요 사항에 답이 있어야 한다. 빠진 것을 보고한다.
- 섹션이 없거나 비어 있거나 막는 질문에 답이 없으면 진행하지 않고, 먼저 Phase A(A-3)를 하도록 안내한다.
- 답이 달린 확인 사항은 **확정 사항**으로 본다.
- 디자인은 Phase A 결과를 기준으로 본다. 섹션 링크는 Phase C 착수 때 받는다.

### 2. 사실 조사 (서브 에이전트, 백그라운드)
백그라운드 서브 에이전트로 실행한다. 조사 결과가 필요 없는 질문(예: 이슈 계층, 브랜치·PR 전략)은 서브 에이전트의 결과를 기다리지 않고 바로 묻는다. 조사 범위:
- 기획서가 말하는 진입점(버튼, 메뉴, 컬럼)이 **실제로 존재하는지**. 기획서는 있다고 가정해도 코드에 없는 경우가 많다.
- 가장 가까운 참고 구현: 비슷한 "버튼 → 모달", "목록 셀 클릭 → 모달", 데이터 조회·변경 패턴
- 검증 유틸, alert/confirm/toast 유틸, 상태 enum과 상수 위치
- **네이밍 충돌**: 새 개념에 붙일 영단어가 기존 코드에서 다른 의미로 쓰이고 있는지
- 탭, 다중 마운트 구조, 전역 이벤트 버스 사용처 (리스너가 중복 실행될 위험)
- 다른 브랜치가 같은 파일을 바꾸고 있는지 (`git branch -a`, `git diff --stat <base>...<branch>`)
- API 계약 없이 화면을 그릴 수 있는지: 기존 목록·응답에 이미 있는 필드

### 3. 크로스체크 게이트 (Phase A 결과 검증)
Phase A는 디자인만 보고 정리한 결과다. 코딩 에이전트는 **코드까지 대조할 수 있으므로**, Phase B에서 스토리 본문을 검증한다. 게이트는 1단계(입력 확인)와 2단계(사실 조사) 뒤에 실행한다. 코드 대조에 사실 조사 결과가 필요하므로, 결과가 돌아온 뒤 게이트를 판정한다. 결과는 판정표로 보여주고, 통과할지 재검증할지는 **사람이 결정한다**.

**체크리스트**
- [ ] 5개 섹션이 모두 있다: 화면 구성, FR, 데이터·필드, 정책·예외, 확인 필요 사항
- [ ] FR마다 진입점과 완료 결과가 있고, 화면 문구가 원문으로 들어 있다
- [ ] 첫 2개 하위 작업을 막는 확인 필요 사항에 답이 있다
- [ ] 디자인과 대조했다: 섹션 링크가 있으면 대조하고, 없으면 "미대조"로 표시한다
- [ ] 코드와 대조했다: 위 2단계의 사실 조사 결과를 쓴다

**불일치 유형과 처리 위치**

| 유형 | 예시 | 처리 |
|---|---|---|
| ① 기획 누락·모순 | 문구 누락, 검증 순서 모호, 번호 형식 충돌 | 기획 담당에게 재검증 → **스토리 갱신** |
| ② 스토리와 디자인 불일치 | 표에 필드가 빠짐, 모드별 표시 항목이 다름 | 해당 섹션 디자인으로 확인 → **스토리 갱신** |
| ③ 기획과 코드 불일치 | 기획이 전제한 컴포넌트가 실제로 없음, 네이밍 충돌, 필드 매핑 모호 | 스토리는 그대로 두고 **질문 라운드와 피처 문서**에 기록 |

③을 스토리에 넣지 않는 이유: 기획 문서에 구현 판단이 섞이기 때문이다.

**분기**
- ①·②가 0건이면 **통과**한다. 바로 질문 라운드로 가고, ③은 질문으로 넘긴다.
- ①·②가 1건 이상이면 **재검증은 한 번만** 한다. 이렇게 해서 무한 루프를 막는다. 그래도 남는 항목은 스토리에 "확인 필요"로 표시하고 다시 재검증하지 않는다. 첫 2개 작업을 막는 항목이 없으면 계속 진행한다. 막는 항목이 있으면 남은 항목을 사람에게 보여주고, 임시값으로 진행할지 담당자 답변을 기다릴지 **사람이 결정한다**.
- `재검증` 블록은 허용된 한 번의 회차에만 추가한다. "최신 회차를 위에"는 사람이 바뀐 스토리로 게이트를 다시 시작할 때에만 해당한다.

**스토리 갱신 방식**
- 위치: 본문 **최상위**, 즉 "관련 문서" 바로 아래이자 "화면 구성" 위에 `## 재검증 (YYYY-MM-DD)` 블록을 추가한다. 회차가 여러 번이면 최신 회차를 위에 둔다.
- 항목 형식: `<섹션/ID>: 기존 → 갱신 (근거: 디자인 노드 / 담당자 확인 / 회의 등)`
- 원본 섹션은 다시 쓰지 않는다. 바뀐 행 끝에 `(→ 재검증 YYYY-MM-DD)` 표시만 단다.
- **서식 보존**: 이슈 트래커의 본문 수정이 전체 교체 방식이면, 원본 서식(예: Jira ADF)으로 읽고 갱신 블록만 끼워 넣은 뒤 같은 서식으로 저장한다. markdown으로 바꿨다가 되돌리면 링크 카드나 서식이 깨질 수 있다.
- 저장하기 전에 갱신 목록을 사람에게 보여주고 확인받는다. 외부에 쓰는 작업이기 때문이다.

> 예시: 어떤 피처에서 ①·②가 0건이고, ③이 3건(기획이 전제한 드롭다운이 없음, 새 개념의 영단어가 기존 코드에서 다른 의미로 쓰임, 금액 필드 후보가 여러 개)이었다. 이 경우 게이트는 통과로 판정하고, ③ 3건은 질문 라운드에서 해결했다.

### 4. 질문 라운드로 결정 수렴
- 라운드마다 **지금 답할 수 있는 질문을 전부** 번호를 붙여 묻고, 질문마다 추천안과 근거를 붙인다.
- 다른 질문의 답에 의존하는 질문은 다음 라운드로 미룬다.
- 조사 결과로 새 결정이 필요해지면 그 라운드에 추가한다.
- 답변에 조건이 붙으면 그 조건이 만드는 새 결정을 다시 묻는다. 예: "기존 버튼 유지" → 새 버튼과 어떻게 공존할지
- 질문 체크리스트:
  - 이슈 계층, 생성 범위와 시점
  - 첫 작업 분리 단위
  - API 계약 미정 대응
  - 브랜치, 커밋, PR 전략
  - 포함할 앱과 흐름의 범위
  - 하위 작업 본문 템플릿, 제목 형식
  - 기존 컴포넌트 교체·공존 방식, 롤백 경로
  - 진입 방식 (셀이 직접 모달 상태를 가질지, 이벤트로 알릴지)
  - 네이밍
  - 공통 유틸 확장 방식 (옵션 추가, 기본 동작 유지)
  - 작업별 검증 범위와 정적 UI 범위
  - 확인용 mock 데이터 주입 방식
  - 모호한 필드 매핑

### 5. 로드맵 분할 원칙
- 01–02: **진입 동선과 레이아웃**. 생성·수정처럼 진입점마다 하나씩 만들고, 이후 작업이 동작만 채우면 되도록 정적 UI 자리를 미리 잡는다.
- 그다음: 진입 검증 → 편집과 실시간 계산 → 부가 동작(정렬 등)
- **API 계약이 필요한 작업은 뒤쪽에 둔다**: 저장·조회·삭제 연동, 필터, mock 제거
- 연쇄 동작(일괄 적용 등)과 다른 앱(파트너용 화면 등)은 맨 뒤에 둔다.
- 상세 본문은 **앞 2개만** 쓴다. 나머지는 제목, FR, In/Out, 참고만 쓰고 착수 직전에 보강한다.

### 6. API 계약 미정 대응
- 기존 목록·응답 데이터를 최대한 활용한다. 생성 모드는 보통 이것만으로 그릴 수 있다.
- 임시 타입과 mock 조회·변경(`Promise` 반환)은 프로젝트 구조에 맞는 위치에 둔다. 교체 지점에는 `// TODO(API)` 주석을 단다.
- 화면에서 확인할 대상이 없으면 개발 환경 전용 가드(예: `process.env.NODE_ENV === 'development'`) 안에서 mock 필드를 주입하고 `// TODO(API) 제거`를 단다. 어느 작업에서 제거할지 로드맵에 적는다.
- 확정되지 않은 필드 매핑은 임시값으로 진행하고 "백엔드 확인" 항목으로 남긴다.

### 7. 하위 작업 본문 템플릿
```
## 목표             (한 줄)
## 관련 FR
## 선행             (앞 작업 키)
## 범위 (In)
## 범위 밖 (Out)    (→ 몇 번 작업으로 넘기는지)
## 참고 구현        (파일:라인)
## 예상 변경 파일   (신규/수정 구분)
## API 의존 (mock 지점)
## 디자인           (섹션 링크 — 사람이 주입 가능)
## 확인 시나리오     (체크박스, 회귀 항목 포함)
## 코드 리뷰 포인트  (롤백 경로, 네이밍, 리스너 정리, 새 코드에만 정리 적용)
## 커밋             (팀 컨벤션 형식)
```
- 제목 형식 예: `[앱][피처명] NN. <진입점> > <내용>`
- 요약만 쓴 작업은 맨 위에 `> 상세 본문은 착수 직전에 보강 예정 / **API 필요**`를 붙인다.
- 다른 브랜치 작업과 겹치면 브랜치, 커밋, 파일을 **"⚠️ 참고 필수"** 섹션에 적는다.

### 8. 브랜치 · 커밋 · PR
- 스토리 브랜치 하나에서 작업한다. 하위 작업은 범위 추적과 판단에 쓴다.
- 커밋 메시지에는 **하위 작업 키**를 넣고, scope는 **피처명으로 고정**한다. 형식은 팀 컨벤션을 따른다.
- 첫 작업이 끝나면 Draft PR/MR을 열고 커밋 단위로 리뷰받는다. 마지막에 PR 하나가 지나치게 커지는 것을 막기 위해서다.

### 9. 기존 코드 보호
- 기존 컴포넌트는 **수정하거나 삭제하지 않고**, 렌더하는 자리만 새 컴포넌트로 바꾼다. 롤백 경로(렌더 복구 한 줄)를 작업 본문에 적는다.
- 기존 로직을 옮길 때는 처음에는 새 컴포넌트 안에 그대로 작성하고, 훅 추출 같은 분리는 나중에 검토한다.
- 기존 컴포넌트와 새 컴포넌트가 **같은 전역 이벤트를 구독하면** 동작이 중복된다(예: 모달이 두 번 열림). 둘 중 하나만 마운트되게 한다.
- import 정렬이나 리팩터링 같은 정리는 **새 코드에만** 한다. 기존 파일은 최소 diff로만 고친다. 다른 브랜치와 충돌하는 것을 막기 위해서다.
- 공통 유틸은 옵션으로만 확장하고 기본 동작은 유지한다.

## Phase C. 하위 작업 단위 구현 (체크포인트 운영)
- 요청: `<하위작업키> 착수해줘` (+ 해당 작업의 디자인 섹션 링크)
- 에이전트 순서:
  1. 하위 작업과 피처 문서를 읽는다
  2. 앞 작업의 커밋 상태를 확인한다
  3. 구현한다
  4. **커밋 전에 멈추고** 확인 시나리오와 코드 리뷰 포인트를 보고한다
- 사람이 확인을 마치면 `커밋해줘` → `다음 작업 보강해줘`(이번 결과를 다음 작업 본문에 반영)
- 피처 문서의 "진행 로그"에 작업별 결과와 다음 작업 반영 사항을 쌓는다.

## 산출물
1. (A) 스토리 본문: 화면 구성 / FR / 데이터·필드 / 정책·예외 / 확인 필요 사항(답변 포함)
2. (B) 하위 작업 N개. 앞 2개는 상세 본문, 나머지는 요약
3. (B) 피처 문서: 로드맵과 키 매핑, 진행 방식, 결정 기록, 조사된 사실, 진행 로그
4. (C) 하위 작업 키 단위 커밋, Draft PR/MR, 진행 로그

## 실행 시 주의 (이슈 트래커 연동)
- 프로젝트마다 하위 작업 이슈 타입 이름이 다르다. 생성 전에 이슈 타입 목록을 조회한다.
- 하나의 트래커에 연결이 여러 개 있으면, 연결마다 권한이 다를 수 있다(읽기는 되는데 쓰기는 403 등). 실패하면 다른 연결로 재시도한다.
- 생성 중 네트워크 오류가 나면 **다시 생성하기 전에** 부모 이슈 기준으로 검색해서 이미 생성됐는지 확인한다. 중복 생성을 막기 위해서다.
- 이슈 생성과 수정은 외부에 쓰는 작업이다. 로드맵과 01–02 본문 초안을 보여주고 확인받은 뒤 실행한다.
