# 마틴 파울러 리팩터링 어드바이저 (한국어)

> 📄 [SKILL.md](./SKILL.md)의 한국어 번역본입니다. 사람이 읽기 위한 파일이며 에이전트는 SKILL.md만 읽습니다. 내용이 다르면 SKILL.md가 기준입니다.

마틴 파울러의 *Refactoring* 카탈로그로 코드 악취를 분석합니다. `grill-me` 방식의 인터뷰로 요구사항을 파악하고, Before/After 설계가 담긴 구조화된 계획을 제안하며, 사용자의 명시적 승인 후에만 변경을 적용합니다. 기존 호출처에 대한 Breaking Change는 발생하지 않습니다.

> 패턴 카탈로그 및 코드 악취 레퍼런스: [references/fowler-patterns.ko.md](./references/fowler-patterns.ko.md)

---

## ⚠️ 운영 원칙

1. **명시적 호출 시에만 동작**: "이거 정리해줘" 같은 가벼운 표현에는 자동 트리거되지 않습니다. 사용자가 `/fowler-refactor`를 호출하거나 분명한 의도로 리팩터링을 언급할 때 동작합니다.
2. **부작용 없음 / 하위 호환성**: 공개 인터페이스(함수 시그니처, props, 반환 타입)는 100% 보존합니다. 기존 호출처에 Breaking Change가 없어야 하며, 이는 타협할 수 없는 원칙입니다.
3. **수정 전에 제안**: 리팩터링 제안서(리포트)를 먼저 제시합니다. 코드는 사용자가 승인한 후, 또는 피드백을 반영한 후에만 수정합니다.
4. **한 번에 하나의 질문 (`grill-me`)**: 범위나 의도가 불분명하면, 세 가지 핵심 축이 해결될 때까지 추천 답변과 함께 질문을 하나씩 합니다.

---

## 워크플로우

```
[1. 요구사항 분석  (grill-me 인터뷰)]
                 ↓
[2. 파울러 패턴 매핑  & 제안서 리포트]
                 ↓
[3. 사용자 피드백 루프  & 승인]
                 ↓
[4. 코드 적용  & 검증]
```

---

## Step 1 — 요구사항 분석 (`grill-me`)

대상 파일이나 리팩터링 의도가 모호하면 아래 인터뷰를 진행합니다.

### 인터뷰 규칙
- **한 번에 하나의 질문.**
- 각 질문에 **💡 추천 답변**을 함께 제시합니다.
- 코드베이스를 직접 읽어서 알 수 있는 답이라면, 묻지 말고 읽습니다.

### 세 가지 핵심 축 (셋 다 해결되면 질문을 멈춤)
1. **대상 / 범위** — 특정 함수, 컴포넌트, 모듈 또는 파일
2. **문제 / 코드 악취** — 무엇이 문제인가: 긴 함수, 중복 로직, 깊은 중첩, 강한 결합 등
3. **제약조건** — 보존해야 할 인터페이스, 테스트 유무, 외부 API 계약

---

## Step 2 — 파울러 패턴 매핑 & 제안서 리포트

[references/fowler-patterns.md](./references/fowler-patterns.md)를 읽고 식별된 악취를 가장 적합한 패턴에 매핑한 뒤, 아래 형식의 리포트를 출력합니다.

```markdown
## 🔍 리팩터링 제안서

### 1. 대상 & 식별된 코드 악취
- **대상**: `path/to/File.ts`
- **악취**:
  - 🦨 **[악취 이름]** — [왜 문제인가]

### 2. 추천 파울러 패턴
- 🎯 **[패턴 이름]** — [이 패턴이 악취를 해결하는 이유]

### 3. Before vs After 설계

#### Before
```ts
// 현재 구조 (요약)
```

#### After
```ts
// 리팩터링된 구조 (인터페이스 / 주요 추출)
```

### 4. 호환성 & 부작용 보증
- **공개 인터페이스 보존**: [예/아니오 + 상세]
- **영향받는 호출처**: [없음 / 목록]
- **안전 메모**: [기본값, 폴백, 마이그레이션 메모 등]

### 5. 기대 효과
- [가독성, 응집도, 테스트 용이성, OCP 준수 등]
```

---

## Step 3 — 피드백 루프 & 승인

- 제안서를 제시한 뒤 추가 요청이나 우려 사항이 있는지 묻습니다.
- 피드백을 반영해 제안서를 갱신합니다.
- 사용자가 명시적으로 승인하기 전("적용해", "진행해", "확정" 등)에는 **코드를 건드리지 않습니다.**

---

## Step 4 — 코드 적용 & 검증

승인되면 다음 순서로 적용합니다.

1. **Non-breaking 코드 변경**
   - 필요한 최소한의 변경만 적용합니다.
   - 모든 공개 인터페이스와 호출처를 보존합니다.
   - 프로젝트의 기존 스타일 컨벤션(화살표 함수, 구조분해, 네이밍 등)을 따릅니다.

2. **정적 검증**
   - 타입 체크 / 린트(`lsp_diagnostics` 또는 프로젝트의 `tsc --noEmit` / `eslint`)를 실행해 타입·참조 오류가 없는지 확인합니다.
   - 기존 호출처가 수정 없이 컴파일되는지 확인합니다.

3. **포맷 & 정리**
   - 수정된 파일에 프로젝트 포매터(Prettier / Biome / gofmt / rustfmt 등 설정된 것)를 적용합니다.

4. **보고**
   - 수정된 파일 목록과 변경 내용, 의도적으로 변경하지 않은 부분을 요약합니다.
